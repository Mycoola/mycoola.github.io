Senior Salesforce Developer Interview Q&A

Michael George  ·  Updated August 2026  ·  6 min read

A living set of the technical deep-dive questions I actually get asked in Senior/Principal Salesforce Developer interviews — with the answers I use. I update this after every interview, so it stays current with what's really being asked in 2026.

Apex & Platform Fundamentals

Q: What's the difference between Queueable Apex and Future methods?

Future methods are simple async calls — they can't chain, and can't accept sObjects directly as parameters (primitive types only). Queueable Apex can chain jobs, accept sObjects/collections, and returns a job ID for monitoring via AsyncApexJob. I default to Queueable for anything beyond a trivial async call.

Q: How do you avoid hitting governor limits in bulk triggers?

Bulkify everything: never put SOQL or DML inside a loop. Use Maps keyed by Id for lookups instead of re-querying. Push heavy logic into Queueable or Batch Apex once the collection size is large. And I always unit test with 200+ record bulk loads, not just single records — that's usually where "works in dev, fails in prod" bugs come from.

Q: Explain the Salesforce sharing model.

Org-Wide Defaults set the baseline access level. On top of that: role hierarchy grants upward visibility, sharing rules extend access by criteria or ownership, manual sharing covers one-off cases, and an Apex sharing layer (__Share objects) handles anything programmatic. For complex multi-business-unit orgs I reach for Account Teams or Territory Management before writing custom Apex sharing.

Q: What is Change Data Capture and when do you use it?

CDC publishes insert/update/delete/undelete events for an object onto the event bus in near-real-time. I use it instead of polling when an external system needs to react to Salesforce data changes — subscribed either via a platform event trigger or an external consumer like a Node.js service or MuleSoft.

Q: How do you test integrations in Salesforce?

HttpCalloutMock for REST, WebServiceMock for SOAP — I never allow a real callout inside a test. I mock the full range of responses, including error scenarios, and explicitly assert on 200, 400, and 500 status code handling, not just the happy path.

OmniStudio

Q: When do you choose OmniStudio over standard Flow?

OmniStudio (OmniScript, Data Mappers/DataRaptors, FlexCards) is built for complex guided interactions and Experience Cloud journeys that need step-based UX, JSON transformations, and reusable components across channels. Standard Flow is a better fit for back-end automation. OmniStudio really shines in Insurance, Health Cloud, and complex service portals where the same logic needs to render across web and mobile.

Debugging Under Pressure

Q: Tell me about the most complex Salesforce bug you ever debugged.

At IQVIA, an integration with a third-party pharma data provider was intermittently failing — no governor limit hits, no exceptions in the logs. I traced it to a race condition in a Queueable chain: bulk-inserted records were spawning multiple jobs that competed for the same external ID. I fixed it with a Batch Apex re-architecture and added a custom Integration_Log__c object so the next failure would be visible immediately instead of requiring another deep trace.

The pattern that keeps coming up: governor limits rarely cause the hard bugs anymore — it's async ordering and race conditions in chained jobs. Know how Queueable, Platform Events, and CDC interact before you walk into a senior-level interview.
