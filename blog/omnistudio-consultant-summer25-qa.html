OmniStudio Consultant — Summer '25 Maintenance Q&A

Updated August 2026  ·  14 questions

This Q&A covers the Summer '25 OmniStudio Consultant certification maintenance module. Topics include the Standard Designer and Design Assistant, SLDS 2 runtime theming, built-in translations, AngularJS deprecation and LWC migration, the Advanced Apex Class Permission Checker, and updated documentation naming.

Standard Designer & Design Assistant

1.How does the OmniStudio Standard Designer help consultants build components faster?

The Standard Designer provides a unified drag-and-drop authoring interface built on Lightning Web Components that replaces the older Angular-based experience. It consolidates Omniscript, Flexcard, Integration Procedure, and DataMapper authoring into one consistent environment, reducing the learning curve for new team members and eliminating the context-switching between different design surfaces.

2.What is the OmniStudio Design Assistant and what problem does it solve?

Design Assistant is a health-monitoring tool built into the Standard Designer that proactively flags issues in Flexcards and Omniscripts — such as broken data sources, deprecated elements, or performance concerns — before they affect end users. It lets consultants audit component health across an org without manually opening each component, making it practical to govern large OmniStudio implementations.

3.What does "monitoring and managing component health" mean in practice with the Design Assistant?

Design Assistant surfaces warnings and errors at the component level — for example, identifying an Omniscript that references a deleted Integration Procedure or a Flexcard with a misconfigured data source. Consultants can review flagged components from a centralized dashboard and prioritize fixes before a release, rather than discovering issues through user-reported bugs.

SLDS 2 & Runtime Experience

4.What is the OmniStudio SLDS 2 theme and how does it enhance the runtime user experience?

SLDS 2 is Salesforce's updated Lightning Design System with a refreshed visual language — updated typography, spacing, and component styles. When applied to OmniStudio apps, it gives Omniscripts and Flexcards a modern, accessible look that matches the rest of the Summer '25 Lightning UI without requiring custom CSS. It also improves accessibility compliance out of the box.

5.What accessibility change replaced the Read-Only property for input elements in OmniStudio?

The Disabled property replaces Read-Only for input elements in Omniscripts and Flexcards. The change aligns OmniStudio's field behavior with SLDS 2 accessibility standards — Disabled is correctly communicated to screen readers and assistive technology, whereas Read-Only was not handled consistently across browsers and input types.

Built-In Translations & Localization

6.How does the built-in translation feature localize single-language Omniscripts and Flexcards?

OmniStudio can now automatically localize label text in single-language components based on the running user's locale setting, without requiring separate translated versions of each component. The platform looks up the user's locale and applies the appropriate translations from a centralized translation workbench entry, so one Omniscript can serve users in multiple languages without duplicating the component.

7.What is the difference between a single-language and a multi-language OmniStudio component, and when does locale-based translation apply?

A single-language component was built with labels in one locale (e.g., English) without explicit translation records for other locales. Built-in translation applies to these by deriving translations from Translation Workbench at runtime. Multi-language components already have explicit translation records per language — those continue to work as before, and the new locale-based fallback is additive, not a replacement.

AngularJS Deprecation & LWC Migration

8.What is the consultant's role in migrating AngularJS-based Omniscripts to LWC?

Consultants need to inventory all active AngularJS Omniscripts in the org, communicate the deprecation timeline and business impact to stakeholders, coordinate the migration effort using Salesforce's migration tooling, and validate that business logic behaves identically after conversion. The migration is a conversion, not a rebuild — but post-migration UAT is essential because some custom JavaScript behaviors may need to be re-expressed as LWC patterns.

9.Why does Salesforce deprecate AngularJS-based Omniscripts rather than continuing to support both frameworks?

AngularJS reached end-of-life in December 2021 and receives no security patches, making it a long-term liability in a multi-tenant platform. Maintaining two rendering engines (AngularJS and LWC) indefinitely doubles the testing surface for every OmniStudio release and prevents Salesforce from delivering LWC-only innovations — such as SLDS 2 and Experience Cloud LWR site support — to the full component catalog.

10.Which deployment targets require LWC-based Omniscripts that AngularJS versions cannot support?

Experience Cloud LWR (Lightning Web Runtime) sites require LWC components and cannot render AngularJS-based Omniscripts. Agentforce integrations similarly depend on LWC-compatible components. Migrating to LWC Omniscripts is therefore a prerequisite for clients who want to embed OmniStudio experiences in modern Experience Cloud sites or extend them into Agentforce workflows.

Advanced Apex Class Permission Checker

11.What is the Advanced Apex Class Permission Checker and how does it affect OmniStudio security?

The Advanced Apex Class Permission Checker validates that a running user's Permission Sets or Permission Set Groups explicitly grant access to any Apex class invoked by an Integration Procedure or Omniscript. Previously, OmniStudio relied primarily on profile-level class access, which could allow Apex execution that wasn't intentionally granted. Enabling this checker closes that gap and aligns OmniStudio with least-privilege security principles.

12.What does a consultant need to do before enabling the Advanced Apex Class Permission Checker in a production org?

Before enabling it, audit all Integration Procedures and Omniscripts that invoke Apex classes and verify that every user group running those components has the required Apex class access granted via Permission Sets — not just via their profile. Enabling the checker without this audit can cause runtime errors for users whose profiles had implicit Apex access that their Permission Sets do not explicitly replicate.

Documentation & Product Naming

13.What documentation naming change did Salesforce introduce and why does it matter for consultants?

Salesforce renamed the OmniStudio documentation guides to distinguish between the standard product ("OmniStudio") and the managed package version ("OmniStudio for Managed Packages"). Consultants need to reference the correct guide for their org's deployment model — implementations using the managed package have different upgrade paths, feature availability timelines, and configuration steps than standard OmniStudio orgs.

14.When would a consultant recommend OmniStudio for Managed Packages vs. standard OmniStudio?

OmniStudio for Managed Packages is used when OmniStudio components are distributed as part of an ISV managed package — for example, an industry cloud solution or a partner app. Standard OmniStudio is for orgs building their own implementations directly. The key differences are release cadence (managed packages are pinned to a package version), upgrade control (the ISV controls when components update), and documentation (separate guides cover each model).
