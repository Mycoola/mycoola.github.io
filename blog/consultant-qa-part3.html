Salesforce Consultant Interview Q&A — Part 3: Automation & Integration Patterns

Updated August 2026  ·  Part 3 of 4  ·  25 questions
Salesforce Consultant Interview Series (100 questions) Part 1: Discovery & Requirements Part 2: Data Model & Sharing Part 3: Automation & Integration Part 4: Migration & Governance

This part covers automation tool selection and integration architecture — the decisions that determine whether a solution stays maintainable as it scales.

Automation Strategy

1.How do you decide between Flow and Apex for a given automation requirement?

Default to Flow for anything declarative tools can express clearly — record updates, simple approvals, screen-guided data entry. Move to Apex when the logic involves complex branching that would make a Flow unreadable, needs a callout with custom error handling, or requires performance that Flow's overhead can't deliver at scale.

2.What are the different Flow types and when is each used?

Screen Flow — guided, user-interactive data collection. Record-Triggered Flow — runs automatically on record create/update/delete, replacing Process Builder and most trigger-based automation needs. Scheduled Flow — runs on a recurring schedule against a batch of records. Autolaunched Flow — invoked from Apex, another Flow, or a Platform Event with no UI.

Flow Type Trigger Has UI? Typical Use Case
Screen Flow User clicks a button/link Yes Guided data entry, wizards, onboarding steps
Record-Triggered Record create / update / delete No Field updates, notifications, cross-object automation
Scheduled CRON / time-based schedule No Nightly batch updates, expiry checks, reports
Autolaunched Apex, Flow, Platform Event, REST No Reusable sub-flows, event-driven processing

3.What is the difference between a before-save and after-save record-triggered Flow?

A before-save Flow updates fields on the triggering record itself without a second database write (fast, no re-triggering other automation on that same object). An after-save Flow can perform actions on related records, call Apex, or send notifications, but incurs the cost of a second save.

4.Why should a team avoid having multiple record-triggered Flows on the same object and event?

Multiple Flows on the same trigger event execute in a somewhat unpredictable relative order (based on an order number that's easy to overlook) and multiply the risk of Flow interviews interacting unexpectedly. Best practice is one Flow per object per triggering event, with internal decision logic to combine different scenarios.

5.What is the recommended migration path for orgs still using Workflow Rules or Process Builder?

Migrate to Flow using Salesforce's official Migrate to Flow tooling where possible, prioritizing by risk/complexity — Salesforce has been retiring Workflow Rules and Process Builder in favor of Flow as the single declarative automation tool, and new automation should never be built on the legacy tools.

6.How do you prevent automation "spaghetti" as an org grows?

Enforce one automation tool of record per object/event combination (documented in a design standard), name Flows/classes descriptively, and maintain an automation inventory/register so new team members can see what already exists on an object before adding to it.

7.What are Flow's known limitations compared to Apex?

Flow struggles with very complex conditional logic (deeply nested decisions become hard to read), lacks robust custom error handling comparable to Apex try/catch, has less efficient bulkification in some versions/patterns, and can't directly implement certain low-level platform APIs that Apex can access.

8.How do you approach approval processes for multi-step, conditional approvals?

Native Approval Processes handle straightforward linear or simple parallel approvals well. For highly dynamic routing (e.g., approver determined by a calculated discount tier that changes per submission), a Screen Flow or Apex-driven approach often provides more flexibility than the native Approval Process builder allows.

Integration Architecture

9.How do you decide between real-time and batch integration for a given requirement?

Choose real-time when the business process depends on immediate data consistency (e.g., checking live inventory before confirming an order). Choose batch when near-real-time is acceptable and volume/cost favor processing in scheduled windows (e.g., nightly financial reconciliation).

10.What is middleware and when would you recommend it over point-to-point integration?

Middleware (like MuleSoft, Dell Boomi, or Workato) sits between systems, handling transformation, orchestration, and routing centrally. Recommend it when integrating three or more systems, since point-to-point integration between many systems creates an unmaintainable web of connections that middleware consolidates into a hub-and-spoke model.

11.What is the difference between Platform Events and Change Data Capture?

Platform Events are custom-defined event messages you publish explicitly from Apex, Flow, or an external system for any business event you define. Change Data Capture automatically publishes events whenever a record changes on a supported standard/custom object, without needing to explicitly author the publish logic.

12.When would you recommend an event-driven integration pattern over a request-response pattern?

When multiple systems need to react to the same change independently (publish-subscribe), or when you want to decouple the source system's availability from the consuming systems' — request-response tightly couples the caller to the immediate availability and response time of the callee.

13.What is API-led connectivity (as popularized by MuleSoft)?

An architecture pattern organizing integrations into three layers — System APIs (direct connection to a backend system), Process APIs (business logic/orchestration across systems), and Experience APIs (tailored to a specific consuming channel) — to maximize reuse and reduce point-to-point coupling.

14.How do you design for integration failure and retries?

Make operations idempotent (safe to retry) using external Ids for upserts, implement exponential backoff for retries rather than immediate hammering, and log every integration transaction (payload, status, timestamp) in a custom object or middleware dashboard so failures are visible and traceable, not silent.

15.What authentication approach would you recommend for a server-to-server integration with Salesforce?

OAuth 2.0 JWT Bearer Flow for unattended, server-to-server integrations — it doesn't require a stored username/password or interactive login, uses a certificate for authentication, and is the recommended pattern for any headless/scheduled integration.

16.What is the difference between the REST API and Bulk API, and when do you use each?

REST API is optimized for smaller, transactional operations (single or few records) with low-latency responses. Bulk API 2.0 is designed for large data volumes (thousands to millions of records), processing asynchronously in batches — using REST API for a bulk load would be far slower and could exhaust API call limits.

17.How do you handle a legacy system that can only push data on a schedule, not in real time?

Design the integration to accept that constraint — use a Scheduled Flow, Batch Apex, or middleware polling job aligned to when the legacy system's export is actually available, and set stakeholder expectations that data will be near-real-time, not live, given the source system's limitation.

18.What is a webhook and how does it fit into a Salesforce integration?

A webhook is an HTTP callback — an external system calls a Salesforce REST endpoint (or a Salesforce Flow/Apex publishes to an external system's webhook URL) when a specific event occurs, enabling near-real-time, event-driven integration without polling.

Solution Design Trade-offs

19.How do you evaluate whether to buy an AppExchange package versus build a custom solution?

Weigh total cost of ownership (license fees vs. build/maintenance hours), how closely the package matches the actual requirement without heavy customization, the vendor's track record and support model, and whether the capability is core-differentiating for the business (worth building) or a commodity capability (better bought).

20.How do you evaluate technical debt trade-offs when a client wants a fast, "quick fix" solution?

Deliver the fast option if truly needed for a deadline, but document the technical debt explicitly (what shortcut was taken and why) and get agreement on when/how it will be revisited — an undocumented shortcut becomes invisible risk, a documented one becomes a planned follow-up.

21.What is a proof of concept (POC) and when do you recommend running one?

A small, time-boxed build validating a specific technical approach or high-risk requirement before committing to full-scale development. Recommend one when a requirement's feasibility is genuinely uncertain (e.g., an unusual integration pattern or a performance-critical design) rather than for well-understood, standard configuration.

22.How do you balance configuration versus customization in a solution recommendation?

Prefer configuration (declarative tools, standard features) as the default since it's easier to maintain, upgrade-safe, and requires less specialized skill to support long-term. Reach for custom code only when configuration genuinely can't meet the requirement, and document why that decision was made.

23.How would you design a solution that needs to work both online and offline (e.g., field service reps)?

Leverage the Salesforce Mobile App's offline data priming capabilities, keep offline-critical data models simple (avoid complex nested queries that don't prime well), and design conflict resolution rules for what happens when the same record is edited both offline and by another user online before sync.

24.What is a common architectural mistake consultants make when designing for future scale?

Over-engineering for a scale the client may never reach, adding unnecessary complexity and cost upfront — versus the opposite mistake of ignoring known scale requirements (e.g., a stated plan to 10x record volume in a year) and designing something that will need a costly rework. The fix is designing to the requirements actually stated, with clearly flagged assumptions.

25.How do you evaluate whether a client's requested integration pattern will scale?

Model the expected data volume and frequency against the chosen pattern's known limits (API call limits, batch size, callout timeout) using realistic growth projections, not just current-day volume, and flag any pattern that's viable today but likely to break within the client's planned growth horizon.
