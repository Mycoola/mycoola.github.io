Salesforce AI Interview Q&A — Part 4: AI Coding Assistants (Claude, Cursor, Copilot)

Updated August 2026  ·  Part 4 of 5  ·  25 questions
Salesforce AI Interview Series (150 questions) Part 1: Agentforce & Agent Design Part 2: Prompt Engineering & Prompt Builder Part 3: LLM/RAG Fundamentals & Trust Layer Part 4: AI Coding Assistants (Claude, Cursor, Copilot) Part 5: Data Cloud AI & Applied Scenarios Part 6: AI Fluency & Human-AI Collaboration

AI-assisted development tools like Claude Code, Cursor, and GitHub Copilot are now a standard part of a Salesforce developer's toolkit — and increasingly a topic in interviews for how effectively a candidate uses them. This part covers the core concepts: skills, hooks, subagents, MCP servers, and how to use these tools responsibly in a professional codebase.

Core Concepts

1.What is an AI coding assistant, and how does it differ from traditional autocomplete?

Traditional autocomplete suggests the next few tokens based on local syntax patterns. An AI coding assistant (Copilot, Cursor, Claude Code) uses an LLM to understand broader intent — generating whole functions, refactoring across multiple files, explaining unfamiliar code, or autonomously executing multi-step tasks like running tests and fixing failures.

2.What is "agentic" coding, and how does it differ from simple code completion?

Agentic coding means the assistant can autonomously plan and execute a multi-step task — reading files, making edits across a codebase, running commands, checking results, and iterating — with minimal human intervention per step, rather than just suggesting one line at a time for a human to accept or reject.

3.What is a "skill" in the context of tools like Claude Code, and why would a team create custom skills?

A skill is a packaged, reusable set of domain-specific instructions and workflow knowledge (often stored as a markdown file with structured guidance) that the assistant can load when a task matches its described trigger conditions. Teams create custom skills to encode project-specific or organization-specific conventions and best practices so every team member's assistant follows the same standards automatically.

4.How is a skill different from a one-off prompt you type into the assistant?

A one-off prompt is ephemeral and must be re-typed (or remembered) every time. A skill is persistent, discoverable, and automatically triggered based on context/description matching — encoding institutional knowledge once so it's reliably applied across every future relevant task, not just the one conversation where you happened to type it.

5.What is a hook in an AI coding assistant's configuration, and what problem does it solve?

A hook is a script or command that automatically fires at a defined lifecycle event (e.g., after every file edit, before a tool call, when a session starts). It solves the problem of enforcing consistent side effects — like auto-running a linter after every edit, or logging every command for audit — without relying on the assistant remembering to do it every time.

6.Give an example of a practical hook you might set up for a Salesforce development workflow.

A post-edit hook that automatically runs a static code scanner (e.g., for CRUD/FLS violations) on any modified Apex class, surfacing issues immediately rather than waiting for a separate manual review step or a CI pipeline failure much later in the process.

Subagents & Orchestration

7.What is a subagent, and why would you delegate a task to one instead of handling it in the main conversation?

A subagent is a separate, often more narrowly-scoped instance of the assistant invoked to handle a specific sub-task — useful for research-heavy or exploratory work (like searching a large codebase) that would otherwise consume a large amount of the main conversation's context, or for giving a task a different, more specialized system prompt/toolset.

8.What is context window management, and why does it matter when working on a large codebase with an AI assistant?

The assistant can only "see" a limited amount of text at once (its context window), so on a large codebase you must be deliberate about what files/history are included in that window — irrelevant content crowds out useful context and can degrade output quality, which is part of why techniques like subagents and targeted file reads exist.

9.What is an MCP (Model Context Protocol) server, and what problem does it solve?

MCP is a standardized protocol that lets an AI assistant connect to external tools and data sources (a database, an issue tracker, an internal API) through a consistent interface, rather than each tool needing a bespoke, one-off integration for every assistant. It solves the fragmentation problem of "every AI tool needs its own custom connector for every external system."

10.Give an example of an MCP server that would be useful in a Salesforce development context.

An MCP server exposing Salesforce CLI operations (querying org data, deploying metadata, describing objects) so the assistant can directly interact with a connected org during a conversation — for example, querying real record data to help debug a reported issue without the developer manually copy-pasting query results back and forth.

11.What is the difference between a tool and an MCP server from the assistant's perspective?

A tool is any individual capability the assistant can invoke (read a file, run a command, query an API). An MCP server is a way of exposing a whole set of related tools (often backed by a specific external system) through one standardized connection — so "MCP server" describes the integration mechanism, while "tool" describes an individual capability it provides.

12.How do custom agent modes (sometimes called "chat modes" or specialized personas) differ from the default assistant behavior?

A custom agent mode configures a specific system prompt, tool access, and behavior profile suited to a narrower purpose (e.g., a "code reviewer" mode restricted to read-only analysis, versus a default mode with full edit/execute capability) — letting teams create safer or more focused variants of the assistant for specific recurring workflows.

Comparing Tools

13.What's the core philosophical difference between an IDE-integrated assistant (like Copilot or Cursor) and a terminal/CLI-based agent (like Claude Code)?

IDE-integrated tools are generally optimized for inline, in-editor suggestions and chat alongside your code. CLI/terminal-based agents are typically built for more autonomous, long-running multi-step tasks (running builds, executing tests, making multi-file changes) with less per-step human intervention — the right choice depends on how much autonomy you want to grant for a given task.

14.What is "YOLO mode" or auto-approval in an agentic coding tool, and what's the risk of enabling it broadly?

It's a setting that lets the assistant execute file edits and commands without requiring approval for each individual action. The risk is that a misinterpreted instruction or a subtle bug in the assistant's reasoning can cause unintended, potentially destructive changes to run unchecked — safer to scope auto-approval narrowly (e.g., only for read-only or clearly reversible actions) rather than enabling it universally.

15.How do you evaluate which AI coding assistant is the right fit for a given team or project?

Consider the team's existing IDE/workflow (does it need to integrate seamlessly, or is a separate CLI tool acceptable), the complexity of tasks you want to delegate autonomously, available integrations (MCP servers, existing skill libraries), and cost model — there's rarely a single universally "best" tool independent of the team's actual working context.

16.What is "vibe coding," and what are its risks in a professional setting?

Vibe coding refers to accepting AI-generated code with minimal review, based on it "seeming" correct, rather than rigorously verifying it. In a professional setting the risk is shipping subtle bugs, security vulnerabilities, or code that violates project conventions — AI-generated code still requires the same review discipline as human-written code, arguably more given its tendency to produce plausible-looking but sometimes subtly wrong output.

Responsible & Effective Use

17.How do you review AI-generated code before merging it, and how does that differ from reviewing human-written code?

The same fundamentals apply — correctness, security, adherence to conventions, test coverage — but you should be specifically alert to AI-typical failure modes: plausible-but-wrong logic, subtly incorrect edge-case handling, or code that looks idiomatic but doesn't actually match the project's established patterns, since the model optimizes for plausibility, not verified correctness.

18.What guardrails should exist around an AI assistant having write access to a production system or codebase?

Require human review/approval before any change reaches production, restrict the assistant's available tools/scope to what's actually needed for the task, and maintain the same code review and CI/CD gates for AI-authored changes as for any human-authored change — AI assistance doesn't remove the need for the safety processes that already exist.

19.How do you prevent sensitive data (API keys, customer PII) from being exposed to an AI coding assistant during a session?

Avoid pasting secrets directly into prompts, use environment variables/secret managers rather than hardcoded values the assistant might read from a file, and be aware of what data a given tool sends to its backend model provider (and under what data retention terms) before granting it broad file-system access.

20.What is prompt injection risk in the context of an AI coding assistant reading untrusted content (e.g., a webpage or an issue description)?

If the assistant reads external, untrusted content as part of a task, that content could contain text specifically crafted to manipulate the assistant into taking unintended actions (like exfiltrating data or running a malicious command) — the same prompt injection risk that applies to any LLM-driven system, so untrusted content sources should be treated with appropriate caution, especially when the assistant has tool-execution capability.

21.How do you measure whether an AI coding assistant is actually improving your team's productivity?

Look beyond raw lines-of-code generated (a weak/misleading metric) toward outcomes like cycle time for typical tasks, defect rates in AI-assisted vs. non-assisted changes, and developer-reported friction — productivity gains that come with a hidden increase in bugs or rework aren't real gains.

Practical Workflows

22.How would you use an AI coding assistant to help understand an unfamiliar, undocumented codebase?

Ask it to summarize the architecture and key entry points, trace how a specific feature flows through the code, or explain a confusing function — treating it as an accelerant for exploration and comprehension, while still verifying its explanations against the actual code rather than accepting them uncritically.

23.How would you use an AI assistant to help write test coverage for an existing, undertested class?

Provide the class and ask it to identify untested branches/edge cases first, then generate tests incrementally, reviewing each for meaningful assertions (not just coverage percentage) — an assistant can quickly draft boilerplate test structure, but the reviewer still needs to confirm the assertions are actually verifying correct behavior.

24.What's an effective strategy for using an AI assistant on a large refactoring task spanning many files?

Break the refactor into clearly scoped, independently verifiable steps rather than asking for one enormous multi-file change at once, review and test after each step, and use the assistant's ability to search/list usages first to understand the full blast radius before making changes.

25.How do you decide when a task is better done manually rather than delegated to an AI coding assistant?

Tasks requiring deep, nuanced business context the assistant doesn't have access to, decisions with high consequences for being subtly wrong, or highly creative architectural judgment calls are often better done (or at least closely driven) by a human — the assistant is most valuable for well-scoped, verifiable, and time-consuming mechanical work.
