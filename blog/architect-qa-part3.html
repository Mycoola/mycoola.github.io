Salesforce Architect Interview Q&A — Part 3: Sharing & Visibility Architecture

Aligned to the Salesforce Sharing & Visibility Architect certification domain, this part covers enterprise-grade security model design decisions.

Sharing Model Fundamentals

1.What is the order of evaluation in the Salesforce sharing model?

Org-Wide Defaults set the baseline (most restrictive starting point), then role hierarchy grants (if enabled per object), then sharing rules, then manual/Apex-managed sharing, and finally team-based sharing (Account/Opportunity/Case Teams) — access is the union of all these grants, and a user's final access is the highest level any applicable rule grants.

Sharing Model — Order of Evaluation

2.What is the difference between object-level, field-level, and record-level security?

Object-level security (profiles/permission sets) controls whether a user can access an object type at all (CRUD). Field-level security controls visibility/editability of specific fields. Record-level security (OWD, sharing rules, role hierarchy) controls which specific records a user with object access can actually see.

3.How do you decide the right Org-Wide Default for a new object?

Start from the most restrictive option that reflects genuine default business need (usually Private), and open access deliberately via sharing rules for known access patterns — retrofitting a restrictive OWD after go-live is far more disruptive than starting restrictive and opening up.

4.What is "Controlled by Parent" sharing and when is it used?

An OWD setting available for detail objects in a Master-Detail relationship, meaning the child record's visibility is entirely determined by the parent's sharing — the child has no independent OWD setting of its own, consistent with Master-Detail's tight ownership model.

5.What is the difference between a criteria-based sharing rule and an owner-based sharing rule?

Owner-based sharing rules grant access based on who owns the record (e.g., all records owned by members of Role A shared with Group B). Criteria-based sharing rules grant access based on field values on the record itself (e.g., all records where Region = 'EMEA' shared with a specific group), regardless of who owns them.

Complex Enterprise Scenarios

6.How would you design sharing for a scenario where a manager needs to see their direct reports' records, but not their peers' or skip-level reports'?

The standard role hierarchy naturally provides this — with "Grant Access Using Hierarchies" enabled, a manager's role sees all roles below it, and access doesn't extend laterally to peers or beyond the hierarchy's natural structure, so this is often achievable without any custom sharing rules at all.

7.How do you design sharing when the org structure (who reports to whom) doesn't match the desired data-visibility structure?

Decouple the two using Public Groups for sharing purposes rather than relying purely on the role hierarchy — the role hierarchy can remain a true reflection of the org chart while sharing rules based on Public Groups implement the actual desired visibility pattern, which may cut across reporting lines.

8.What is Apex-managed sharing and when would you use it instead of declarative sharing rules?

Sharing granted programmatically via __Share object records inserted by Apex, used when the access logic is too dynamic or complex for declarative sharing rules to express — for example, sharing based on a calculated business condition that changes frequently or depends on multiple related object states.

9.What is the difference between implicit and explicit sharing on related objects (e.g., Opportunity and its Account)?

By default, users with access to an Opportunity implicitly gain read access to its related Account (and vice versa, in some configurations) even without an explicit sharing rule on the Account itself — this implicit sharing behavior needs to be understood since it can grant more access than an architect might expect from the Account's OWD/sharing rules alone.

10.How would you design a security model for a scenario where external partners need to see a subset of Opportunities but never each other's data?

Use an Experience Cloud partner community with a restrictive OWD, Sharing Sets or Share Groups tied to the partner's Account/Contact, and validate that guest/partner user profiles have no broader object access than strictly required — partner isolation failures are a common security review finding.

11.What are Account Teams, Opportunity Teams, and Case Teams, and when would you recommend them?

These are native features letting individual users be added to a specific record's collaborative "team" with defined access levels, ideal for ad hoc, per-record collaboration (e.g., a deal desk specialist added to one specific Opportunity) rather than a broad, rule-based sharing pattern.

12.How does sharing work differently for high-volume community/portal users compared to standard internal users?

High-volume community users don't have roles and can't be placed in the role hierarchy (for scalability reasons, since role-based sharing recalculation doesn't scale to millions of external users) — their access is managed instead through Sharing Sets, which map their profile/criteria to specific record access rather than hierarchy-based visibility.

Encryption & Data Protection

13.What is Shield Platform Encryption and what does it protect against?

A feature that encrypts data at rest using an org-specific key, protecting against certain threat vectors like unauthorized database-level access, while preserving most standard Salesforce functionality (search, some automation) on encrypted fields — it's not a substitute for access control, since properly authorized users still see decrypted data.

14.What is the difference between Shield Platform Encryption and Classic Encryption?

Classic Encryption (legacy, custom text fields only) offers basic masking with very limited platform feature compatibility. Shield Platform Encryption is the modern, more capable option supporting a broader range of standard/custom field types with better compatibility with search, reports, and other platform features.

15.What are the limitations to be aware of when encrypting fields with Shield Platform Encryption?

Certain automation and features (some formula fields, certain API/integration behaviors, specific search index behaviors) have restrictions or altered behavior on encrypted fields — architects must validate that encryption doesn't silently break a required business process before enabling it broadly.

16.What is Field-Level Security versus encryption — are they solving the same problem?

No — FLS controls whether a user can see/edit a field at all based on their permissions. Encryption protects the data at the storage/infrastructure layer against threats that bypass normal application access controls (e.g., a database-level breach). A properly authorized user with FLS access sees the decrypted value regardless of encryption.

17.How do you decide which fields need encryption versus which just need strict FLS?

Encrypt fields containing highly sensitive regulated data (SSN, health records, financial account numbers) where infrastructure-level protection is a compliance requirement. Rely on FLS alone for sensitive-but-not-regulated business data where access control (not infrastructure-layer protection) is the actual requirement.

Auditing & Monitoring

18.What is Field Audit Trail (part of Shield) and how does it differ from standard Field History Tracking?

Standard Field History Tracking retains a limited history window and a limited number of tracked fields per object. Field Audit Trail (a Shield feature) extends retention up to 10 years and increases the number of trackable fields, supporting longer-term compliance and audit requirements.

19.What is Event Monitoring and how does it support a security architecture?

Event Monitoring captures detailed logs of user activity (logins, API calls, report exports, Lightning page views) that can be analyzed for anomalous behavior — useful for detecting potential data exfiltration or investigating a security incident after the fact.

20.How would you architect detection for a user who's exporting unusually large volumes of data?

Use Event Monitoring's report/API export events combined with Transaction Security Policies to automatically flag, block, or require additional authentication when export volume for a single user exceeds a defined threshold in a given period.

21.What is a Transaction Security Policy and what can it enforce?

A Shield feature letting you define real-time rules that trigger an action (block, notify, require MFA) in response to specific user behaviors — such as a login from an unusual location, or bulk data export exceeding a threshold — enforced automatically without waiting for after-the-fact log review.

Guest User & External Access Risk

22.Why is Guest User access a common security risk area, and how do you mitigate it?

Guest User profiles (used for unauthenticated Experience Cloud site visitors) are sometimes over-permissioned during initial site setup and forgotten. Mitigate by regularly auditing Guest User profile object/field/record access against the strict minimum needed for public pages, and disabling any "View All"/broad sharing that shouldn't apply to anonymous users.

23.What is the Health Check tool and what does it assess?

A built-in Salesforce tool that scores an org's security configuration against Salesforce's recommended baseline (password policies, session settings, and other org-wide security settings), flagging deviations that increase risk — a useful periodic architectural review step.

24.How do you architect access for an integration user account to follow least-privilege principles?

Create a dedicated integration user (never reuse a real employee's login) with a minimal permission set granting only the specific object/field access the integration actually needs, and avoid granting "Modify All Data" or broad admin permissions purely for convenience.

25.How would you design and validate a comprehensive security review process for a new Salesforce implementation before go-live?

Combine automated tooling (Health Check, a static analysis scan for CRUD/FLS gaps in custom code) with a manual review of OWD/sharing rules against the documented requirements, a penetration-style review of any custom-exposed endpoints (Sites, Experience Cloud, REST resources), and a sign-off checklist covering encryption, guest access, and integration user permissions before production release.
