Salesforce Flow & Automation Q&A

August 2026  ·  Original notes based on Salesforce documentation

Notes on declarative automation: Flow Builder's building blocks, record-triggered flows, decision logic (including decision tables and matrices), and how to choose the right automation tool for a given requirement.

1.How should you decide between a record-triggered flow, a screen flow, and Apex?

Record-triggered flows suit backend automation reacting to data changes; screen flows suit guided user interactions; Apex suits logic too complex, performance-sensitive, or programmatically testable for declarative tools. The decision hinges on who initiates the process and how complex the logic is.

2.What is the difference between a before-save and an after-save record-triggered flow?

A before-save flow can update the triggering record's own fields without a second save operation, making it faster for simple field updates. An after-save flow can update related records and trigger further automation, needed for anything beyond the current record.

3.Why do entry conditions matter as much as the flow's actual logic?

Entry conditions determine whether the flow runs at all. Loose or missing entry conditions cause a flow to fire for irrelevant changes, wasting resources and increasing the risk of recursion or unintended side effects on unrelated updates.

4.What is the purpose of a subflow?

A subflow lets one flow call another, reusable flow — similar to calling a function. This avoids duplicating the same logic across multiple parent flows and centralizes maintenance to one place when that shared logic changes.

5.How do loops in Flow differ from loops in Apex in terms of risk?

A loop in Flow that contains a DML or query element inside it can hit governor limits just as easily as un-bulkified Apex — Flow doesn't automatically bulkify DML placed inside a loop, so the same "collect first, then act once" discipline applies.

6.What problem do decision tables and decision matrices solve compared to a long chain of Decision elements?

They let you express many condition/outcome combinations as structured rows rather than a nested tree of if/else branches, which is easier to read, maintain, and update (including via CSV import) as the number of business rules grows.

7.Why does the order in which automations run matter for a single object?

If multiple flows, validation rules, and triggers act on the same object, execution order determines what data each one sees. Salesforce documents a specific save order, and designs that assume a different order can produce inconsistent results.

8.What is the value of using Flow features like Get/Update/Create Records versus writing equivalent Apex?

These elements let admins and lower-code developers implement CRUD-style automation without writing or maintaining code, at the cost of some flexibility and performance control compared to hand-written, bulk-optimized Apex.

9.Why should automation documentation matter as much as the automation itself?

Flows built by different people over time can silently interact. Clear naming, descriptions, and documented entry conditions make it possible for someone new to the org to understand what will fire and why before making a change that could conflict with existing automation.
