Salesforce Apex Fundamentals Q&A

August 2026  ·  Original notes based on Salesforce developer documentation

Core Apex concepts drawn from a large set of Salesforce developer documentation, blog posts, and tutorials: the language itself, querying with SOQL/SOSL, triggers, DML, governor limits, and sharing keywords.

1.What is Apex, and when should it be used instead of declarative tools?

Apex is Salesforce's strongly typed, on-platform programming language. It's used when logic is too complex for Flow (deep loops, complex transaction control, callouts combined with intricate business rules) or when reusable, testable code is preferable to a large declarative automation.

2.What is the difference between SOQL and SOSL?

SOQL queries one object (and its relationships) with precise field and filter control, similar to SQL. SOSL performs a full-text search across multiple objects and fields at once, better suited to a broad "find this term anywhere" search than a targeted query.

3.What is a governor limit, and why does Salesforce enforce them?

Governor limits cap resource usage per transaction — SOQL queries, DML statements, CPU time, heap size — to keep the multi-tenant platform fair and stable so one org's runaway code can't degrade performance for others sharing the same infrastructure.

4.Why does bulkifying Apex code matter so much?

Triggers and batch operations can process hundreds of records in a single transaction. Code written assuming only one record (SOQL/DML inside a loop) will hit governor limits at scale, so Apex must be written to handle collections, not single records, from the start.

5.What's the difference between "with sharing," "without sharing," and "inherited sharing"?

"With sharing" enforces the running user's record-level sharing rules; "without sharing" ignores them and runs with full object access; "inherited sharing" uses whichever mode the calling context already has, useful for utility classes that shouldn't dictate their own security model.

6.Why is enforcing object and field permissions separate from enforcing sharing?

Sharing controls which records a user can see; object/field-level security controls which objects and fields they can access at all. Apex run in system context bypasses both by default, so code that acts on behalf of a user should explicitly check or enforce these permissions.

7.What is SOQL injection, and how is it prevented?

SOQL injection happens when untrusted input is concatenated directly into a query string, letting an attacker alter the query's logic. Using bind variables or the `String.escapeSingleQuotes` method (or dynamic SOQL built safely) prevents user input from being interpreted as query syntax.

8.Why do sObjects that don't support DML need special handling?

Some sObjects (certain read-only, setup, or metadata-related objects) can't be inserted, updated, or deleted via standard DML — code interacting with them must use other mechanisms (Metadata API, Tooling API, or platform-specific methods) instead of assuming a uniform DML interface.

9.What is the practical difference between Limits.getLimit() plus startTest()/stopTest() when testing Apex?

startTest()/stopTest() resets governor limits for the code inside the block and forces any asynchronous work (future methods, queueables, batch jobs) to run synchronously before stopTest() returns, letting a test assert on results that would otherwise complete later.

10.Why is a class variable's visibility (private/public/global) a design decision, not just a formality?

A class's members define its contract with other code. Overly public members invite unintended coupling, while overly private ones block legitimate reuse — matching visibility to intended consumers (same class, same package, or global API) keeps the codebase's dependencies deliberate.
