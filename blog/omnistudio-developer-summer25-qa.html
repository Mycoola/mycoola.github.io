OmniStudio Developer — Summer '25 Maintenance Q&A

Updated August 2026  ·  14 questions

This Q&A covers the Summer '25 OmniStudio Developer certification maintenance module. Topics include the Standard Designer, OmniOut deployment, Node.js version updates, AngularJS deprecation, Connect APIs, the Navigate Action element, and enhanced Apex permission checks.

Standard Designer & List View

1.What is the OmniStudio Standard Designer and how does it differ from the previous experience?

The Standard Designer is OmniStudio's updated authoring environment built on Lightning Web Components. It replaces the older Angular-based experience with a unified interface for building Omniscripts, Flexcards, Integration Procedures, and DataMappers — using the same design language as the rest of Salesforce Setup, which reduces context-switching for developers.

2.How does the OmniStudio list view help manage components at scale?

The list view lets you search, filter, and sort all OmniStudio component records (Omniscripts, Flexcards, Integration Procedures, DataMappers) from a single screen. You can filter by type, status, or owner without opening each component, which makes auditing and bulk management much faster in large orgs with hundreds of components.

3.Where can the Lightning Rich Text Editor be used in OmniStudio?

The Lightning Rich Text Editor is available as an element inside Omniscripts and as a card action inside Flexcards. It allows end users to enter formatted text at runtime — including bold, italic, lists, and links — without the developer needing to build a custom LWC for that input type.

Connect APIs & Integration

4.What are OmniStudio Connect APIs and why do they improve Apex integration?

Connect APIs expose OmniStudio component execution (Omniscripts, Integration Procedures, DataMappers) as standard REST endpoints. They let Apex code invoke OmniStudio logic directly via HTTP without custom wiring, which decouples the Apex layer from OmniStudio internals and makes the integration easier to test and maintain independently.

5.How does error logging work in Integration Procedures and how do you enable it?

Error logging captures the inputs, outputs, and error messages of Integration Procedure executions into platform log records. You enable it by turning on the error logging flag on the Integration Procedure record itself. Once enabled, failed executions produce queryable log entries that let you diagnose exactly which action element failed and what the runtime data looked like.

6.How do you configure a DataMapper Load to use an external data source?

In the DataMapper Load configuration, you set the target to an External Object or use an HTTP Action to push data to an external system instead of Salesforce objects. The DataMapper handles field mapping and transformation; the external data source connection is defined via Named Credentials or External Services, keeping credentials out of the component configuration.

OmniOut & Node.js

7.What is OmniOut and what problem does it solve?

OmniOut is the OmniStudio toolset for deploying Omniscripts and Flexcards outside of Salesforce — for example, on a public-facing website or a non-Salesforce portal. It compiles OmniStudio components into standalone LWC bundles that can run without a Salesforce session, enabling self-service experiences for unauthenticated users.

8.Why did Summer '25 update the Node.js version requirement for OmniOut?

Node.js 18 reached end-of-life, so OmniOut now requires Node.js 20 or 22 (specifically 22.11.0+ for the latest LTS). Running on an unsupported Node.js version exposes the build environment to unpatched security vulnerabilities and can cause incompatibilities with updated build tooling. Upgrading ensures the OmniOut build pipeline remains secure and receives continued upstream support.

9.What other tool version requirements changed alongside Node.js in the OmniOut build environment?

The OmniStudio Build Tool was updated to version 1.17.11 or higher, and Puppeteer was upgraded to version 21.11.0. Puppeteer is used by the build tool to render and snapshot components during the compilation process, so keeping it current ensures compatibility with the updated Chromium engine it depends on.

AngularJS Deprecation

10.Why are AngularJS-based Omniscripts being deprecated?

AngularJS reached end-of-life in December 2021 and is no longer maintained by Google, meaning no security patches or updates. Salesforce deprecated AngularJS-based Omniscripts to move the entire OmniStudio component model to the LWC framework, which is the Salesforce-supported standard and aligns with the broader platform direction away from third-party JavaScript frameworks.

11.What is the migration path from AngularJS-based Omniscripts to the LWC framework?

Salesforce provides a migration tool that converts existing AngularJS Omniscripts to LWC-based equivalents. Developers should audit their org for any active AngularJS Omniscripts, run the migration utility, test the converted components in a sandbox, and promote them through their deployment pipeline before the deprecation deadline removes AngularJS rendering support.

Apex Permission Checks & Navigate Action

12.What is the enhanced Apex class permission check in OmniStudio and why does it improve security?

OmniStudio now performs stricter checks on which Apex classes a running user has access to before executing them via Integration Procedures or Omniscripts. The PerformAdvancedCheck flag enables validation against the user's Permission Sets and Permission Set Groups rather than relying solely on profile-level class access. This closes a gap where users could previously trigger Apex execution they weren't explicitly granted access to.

13.What changed in the Navigate Action element's behavior in Omniscripts?

The Navigate Action element was updated to support more precise navigation between steps, including the ability to target a specific step by name rather than only moving forward or backward sequentially. This enables conditional navigation flows — for example, skipping a step based on user input — without requiring a custom LWC or JavaScript workaround.

14.How does the Navigate Action change affect existing Omniscript designs that relied on the old behavior?

Existing Omniscripts that use Navigate Action elements should be tested after upgrading to confirm that step targeting still resolves as expected. If a script relied on implicit sequential navigation, the new named-step targeting is additive and won't break existing behavior — but any script using step names for navigation should be validated to ensure names haven't changed during migration to the Standard Designer.
