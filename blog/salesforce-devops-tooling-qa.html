Salesforce DevOps & Developer Tooling Q&A

August 2026  ·  Original notes based on Salesforce Developers documentation

Notes on the Salesforce development lifecycle: source-driven development, packaging, sandboxes, the retirement of legacy migration tools, and the VS Code extension ecosystem.

1.Why did Salesforce move teams from the Ant Migration Tool to the sf CLI?

The sf CLI supports source-driven development with modern package-based deployment, scratch orgs, and CI/CD integration, whereas the Ant Migration Tool was built around older change-set style deployment — the shift reflects the platform's move toward standard software delivery practices.

2.What is the practical difference between a scratch org and a sandbox?

A scratch org is a temporary, source-defined org spun up from a definition file for short-lived development/testing — cheap and disposable. A sandbox is a longer-lived copy of an existing org (with varying levels of data/config), suited to ongoing testing against realistic org state.

3.Why does package-based development change how a team thinks about metadata?

Instead of deploying loose metadata directly, package-based development organizes functionality into versioned, installable packages — making dependencies explicit and enabling safer incremental upgrades across orgs that install the same package.

4.What's the difference between an unlocked package and a managed package?

Unlocked packages are typically used for internal, org-specific modularization with fully visible, editable source after install. Managed packages (used by ISVs) protect intellectual property and support formal versioned upgrades for external distribution.

5.Why does an org-dependent unlocked package exist as a separate concept from a regular unlocked package?

An org-dependent unlocked package can reference metadata that already exists in the target org (rather than being fully self-contained), useful for large legacy orgs incrementally adopting package-based development without extracting every dependency first.

6.What value does Salesforce Code Analyzer add beyond manual code review?

Code Analyzer runs automated static analysis (via PMD, ESLint, and other engines) to catch security and quality issues consistently across a codebase, catching classes of bugs that are easy to miss in ad hoc manual review, especially at scale.

7.Why would a team invest in VS Code extensions rather than the built-in Setup UI for development?

The Salesforce Extensions for VS Code provide source control integration, local testing, debugging, and metadata deployment workflows that support proper software engineering practices — version history, code review, and repeatable deployments — that Setup UI editing doesn't provide.

8.What is Code Builder, and why would a developer choose it over a local VS Code install?

Code Builder is a browser-based IDE running entirely in the cloud, useful when a developer needs a consistent environment without local setup — for example, working from a restricted or shared machine where installing local tools isn't practical.
