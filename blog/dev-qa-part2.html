Salesforce Developer Interview Q&A — Part 2: Triggers, Bulkification & Async Apex

Updated August 2026  ·  Part 2 of 4  ·  25 questions

This part covers the most heavily tested Developer topics: trigger design, bulk-safe coding, and the four asynchronous Apex execution contexts.

Triggers & Bulkification

1.What are the trigger execution events in Apex?

before insert, after insert, before update, after update, before delete, after delete, and after undelete. "Before" events let you modify the record before it's saved; "after" events give you the committed record Id and let you act on related records.

2.Why should you never put SOQL or DML inside a for loop?

Each iteration of a loop over a bulk operation (e.g., 200 records from a Data Loader batch) would issue its own query or DML statement, quickly exceeding the 100-SOQL-query or 150-DML-statement per-transaction governor limits. Always collect data into a Set/Map first, query or perform DML once outside the loop.

3.What is a bulkified trigger?

A trigger written to correctly and efficiently process any number of records (1 to 200 per batch) in a single execution, using collections and single SOQL/DML statements instead of per-record queries — so it behaves identically whether it fires from a UI save or a 10,000-record bulk API job.

4.What is Trigger.new and Trigger.old?

Trigger.new holds the list of new/updated record versions (writable in before triggers). Trigger.old holds the list of record versions before the change (read-only). In delete triggers only Trigger.old is populated.

5.What is Trigger.newMap used for?

It's a Map<Id, SObject> giving O(1) lookup of a record by Id inside the trigger context — commonly used in after update to compare the new vs. old value of a field for a specific record without looping to find it.

6.How do you prevent recursive trigger execution?

Use a static Boolean (or a static Set of processed record Ids) in a helper class that's checked at the start of the trigger/handler and set to true before any DML that could re-fire the trigger. Static variables persist for the duration of the transaction, so this reliably blocks a second pass within the same transaction.

7.What's the recommended trigger design pattern?

One trigger per object (avoiding multiple triggers with unpredictable order), which delegates immediately to a handler class implementing the business logic per event. This keeps the trigger itself nearly empty, keeps logic testable in isolation, and gives a single place to control execution order and recursion guards.

8.What happens if an exception is thrown in a trigger?

The entire transaction is rolled back, including any DML already performed earlier in that transaction (even in unrelated objects), unless the exception is caught and handled. In bulk operations, a single record's failure without proper partial-success handling can fail the whole batch.

9.What is Database.insert(records, false) used for?

The second parameter (allOrNone) set to false allows partial success — records that fail validation don't roll back records that succeed. The method returns a list of Database.SaveResult objects you can inspect to see which records failed and why, which is essential for bulk data-load tolerance.

10.What are the key governor limits a developer should always keep in mind?

100 SOQL queries per transaction (200 for async), 150 DML statements, 50,000 records retrieved by SOQL, 10,000 DML rows, 6MB heap size (12MB for async), and 10 seconds of CPU time (60 for async). Bulkified code respects these regardless of batch size.

Asynchronous Apex

11.What are the four types of asynchronous Apex?

Future methods (simple fire-and-forget async), Queueable Apex (chainable, accepts complex types), Batch Apex (processes massive record volumes in chunks), and Scheduled Apex (runs on a cron-like schedule).

12.What is a Future method and what are its limitations?

A method annotated @future that runs asynchronously in its own thread and transaction. Limitations: parameters must be primitive types or collections of primitives (no sObjects), it can't be chained to another future call, and it doesn't return a monitorable job Id.

13.What is Queueable Apex and how is it different from Future methods?

Queueable Apex is a class implementing the Queueable interface. Unlike Future methods, it can accept complex/non-primitive types including sObjects, can be chained (one Queueable enqueuing another), and returns a job Id via System.enqueueJob() that can be tracked in AsyncApexJob.

14.When would you use Batch Apex instead of Queueable?

When you need to process a very large number of records (thousands to millions) that exceed normal transaction limits, since Batch Apex automatically splits the record set into governor-limit-safe chunks (default 200) via start/execute/finish methods. Queueable is better for smaller, more immediate async work.

15.What are the three methods every Batch Apex class must implement?

start() — returns a Database.QueryLocator or iterable defining the full record set. execute() — processes one chunk (scope) of records at a time. finish() — runs once after all chunks complete, useful for sending a summary email or chaining another job.

16.What is Scheduled Apex and how do you schedule a job?

A class implementing the Schedulable interface with an execute() method, registered to run at a specific time using a CRON expression via System.schedule('JobName', cronExpr, new MyClass()), or through the Setup UI.

17.Can you chain Batch Apex jobs?

Yes — call Database.executeBatch() for the next batch job from inside the finish() method of the current one. This is a common pattern for multi-stage data processing pipelines.

18.What is the maximum number of Queueable jobs you can chain?

In most orgs you can chain Queueable jobs up to a depth of 5 in some limited contexts, but for standard (non-test) execution, chaining depth is effectively unlimited as of newer API versions, though each still respects per-transaction governor limits — so chaining isn't a way to bypass limits, just to sequence separate transactions.

19.What is Platform Cache and how does it help asynchronous processing?

Platform Cache stores data in a distributed, in-memory cache that persists across transactions (org cache) or within a single user's session (session cache). It reduces redundant SOQL/callouts by letting async and sync transactions share computed or fetched data without re-querying.

20.What happens if you exceed the number of queued/executing Batch jobs allowed?

Salesforce enforces a limit on concurrent Apex flex/batch jobs per org (typically 5 active concurrently, with a queue for the rest). Exceeding the total daily async Apex method executions or attempting to queue beyond the concurrent limit throws a LimitException.

21.How do you make a callout from a trigger?

You can't make a synchronous HTTP callout directly from a trigger context. Instead, wrap the callout logic in a @future(callout=true) method or a Queueable class implementing Database.AllowsCallouts, and invoke that from the trigger.

22.What is the difference between a stateful and stateless Queueable class?

By default, Queueable instance variables don't persist across chained jobs unless the class implements Database.Stateful. A stateful Queueable retains its member variable values from one chained execution to the next — useful for running totals across a chain.

23.What is the Limits class used for?

The built-in Limits class (e.g., Limits.getQueries(), Limits.getLimitQueries()) lets you programmatically check current governor limit consumption at runtime, useful for defensive coding in loops that process unpredictable data volumes.

24.How would you process 1 million records without hitting limits?

Use Batch Apex with an appropriately small scope size (e.g., 200), a selective QueryLocator in start() to avoid the 50-million-row batch query limit, and bulkified logic in execute(). For extremely large volumes, consider Bulk API 2.0 outside of Apex entirely for the ingestion piece.

25.What's the difference between synchronous and asynchronous governor limits?

Async contexts (Future, Queueable, Batch execute) generally get roughly double the synchronous limits — e.g., 12MB heap vs. 6MB, 60s CPU time vs. 10s — because they're expected to handle heavier processing loads outside the constraints of a user waiting on a page.
