Salesforce Flow Interview Q&A — Part 1: Branching Elements & Decision Logic

Updated August 2026  ·  Part 1 of 1  ·  25 questions
Salesforce Flow Interview Series (25 questions) Part 1: Branching Elements & Decision Logic

Flow Builder questions increasingly come up in both Developer and Consultant rounds as declarative automation takes on more of the logic that used to live in Apex triggers. This part covers the branching elements — Decision, and the newer Split by Field Value and Split by Date elements — and the design judgment behind choosing between them.

Decision Element Fundamentals

1.What is the Decision element used for in Flow Builder?

It branches a flow's execution path based on one or more conditions, evaluating each configured outcome in order and routing to the first one whose criteria are met, or to the default outcome if none match.

2.Can a single Decision outcome test multiple conditions at once?

Yes — a Decision outcome supports compound criteria combined with AND/OR logic, which is what distinguishes it from the newer single-condition Split elements.

3.In what order does a Decision element evaluate its outcomes?

Top to bottom as configured — the flow routes to the first outcome whose conditions evaluate to true, so outcome order matters when criteria could overlap.

Split by Field Value

4.What problem does the Split by Field Value element solve?

It gives a simpler, more readable way to branch on the possible values of a single field or resource, without needing to configure a full Decision element for what is fundamentally a single-condition branch.

5.How does Split by Field Value handle values that don't match any configured path?

It routes them down a built-in Default Path, similar in concept to a Decision element's default outcome.

6.Can the Default Path in Split by Field Value be renamed?

No — unlike the other configured paths, the default outcome's name is fixed and can't be customized.

7.What convenience feature does Split by Field Value offer for configuring many similar paths?

A Clone button, which duplicates an existing path so you can quickly adjust it for a new value rather than building each path from scratch.

8.What is the core limitation of Split by Field Value versus Decision?

It only supports evaluating a single field or resource per path — it can't combine multiple criteria within one path the way a Decision outcome can.

Split by Date

9.What release introduced the Split by Date element?

Winter '27, alongside Split by Field Value.

10.What comparison operators does Split by Date support?

Before, Between, After, and Is On.

11.How does Split by Date compare to Split by Field Value in terms of resource flexibility?

It's more flexible — each path can compare against a different date value or resource, whereas Split by Field Value is scoped to evaluating a single field or resource across its paths.

12.What's a good real-world scenario for Split by Date?

Branching on SLA deadlines, contract renewal windows, or record aging — any logic where the only deciding factor is how a date relates to today or another date value.

13.Does Split by Date allow combining a date condition with another unrelated condition in the same path?

No — like Split by Field Value, each path only evaluates the one condition it's built for; a second, independent condition requires the Decision element instead.

Choosing the Right Element

14.When should you reach for a Split element instead of Decision?

When the branch is genuinely single-condition — one field's value or one date comparison — since Split elements make that intent clearer on the canvas than a Decision element configured with a single criterion per outcome.

15.When must you use Decision instead of a Split element?

As soon as a single path needs more than one condition to be true simultaneously — Split elements have no mechanism for compound, multi-criteria logic within a path.

16.Is it possible to migrate an existing Decision element to a Split element?

Not automatically — since Split elements can only express single-condition branches, migration is only viable if every outcome in the existing Decision is already based on one field or one date condition; otherwise the logic must stay in Decision.

17.How do Split elements affect flow readability for other maintainers?

By making single-condition intent explicit in the element's name and configuration, a maintainer can tell at a glance that a branch is simple, without having to open a Decision element and read through its criteria to confirm there's no compound logic hiding inside it.

Design & Governance

18.Why might a team standardize on using Split elements wherever possible?

To keep flows self-documenting — a Split element signals "single condition" by design, reducing the chance that a reviewer misses a compound condition buried inside what looks like simple branching logic in a Decision element.

19.What risk exists if a team overuses Decision elements for simple, single-field branches?

Flows become harder to scan quickly, since every branch requires opening the Decision element's configuration to confirm whether it's actually simple or hiding additional criteria — a consistency and maintainability cost as the org's flow library grows.

20.How would you explain the trade-off between Split elements and Decision to a junior flow builder?

Split elements trade flexibility for clarity — they can express less, but what they do express is immediately obvious; Decision can express anything, but that power comes at the cost of needing to actually inspect the configuration to know what it's doing.

Practical Scenarios

21.You need to branch a flow based on whether an Opportunity's Stage is one of five values. Which element fits best?

Split by Field Value — a single field with several possible values, and no compound condition needed per branch, is exactly the case it was built for.

22.You need to branch based on whether a Case's Due Date is overdue, due today, or due later. Which element fits best?

Split by Date, using Before/Is On/After comparisons against today's date across the three paths.

23.You need to branch based on whether an Account's Industry is "Healthcare" and its Annual Revenue exceeds a threshold. Which element fits best?

Decision — this requires two conditions combined within the same path, which neither Split element supports.

24.A flow currently uses a Decision element with five outcomes, each testing only one picklist value. Would you refactor it?

It's a reasonable candidate to refactor into Split by Field Value, since every outcome is already single-condition — the refactor would improve readability without losing any logic.

25.How would you justify introducing Split elements to a team that's comfortable with Decision and sees no need to change?

Frame it as a readability and code-review improvement, not a capability upgrade — Split elements don't do anything Decision can't already do for single-condition branches, but they make that simplicity visible at a glance, which reduces review time and the chance of a maintainer missing hidden compound logic later.
