Split by Field Value & Split by Date: Salesforce Flow's Simpler Branching Elements

Michael George  ·  August 2026  ·  5 min read

Winter '27 added two new branching elements to Flow Builder: Split by Field Value and Split by Date. Both are streamlined alternatives to the Decision element for the common case where you just need to branch on a single field or date — no compound conditions required. This post breaks down how each works, how they differ from Decision, and when to reach for which.

Resource

Split by Field Value and Split by Date Elements in Salesforce Flow

Split by Field Value

This element evaluates a single field or resource and creates a separate outcome path for each configured value, plus a built-in Default Path for anything that doesn't match. It supports a Clone button to quickly duplicate a path when you need several similarly-shaped branches, though the Default Path itself can't be renamed.

Split by Date

This element branches based on date comparisons, offering four operators: Before, Between, After, and Is On. Each path can compare against a different date value, and it's more flexible than Split by Field Value when it comes to resource selection — useful for date-driven branching like SLA windows, renewal timing, or aging logic.

The Key Limitation

Neither element lets you define multiple criteria within the same path — that's the line that separates them from the Decision element. A Split element path can only test one condition. The moment your logic needs "field value is X and some other condition is also true" within the same branch, Split elements can't express it and you need Decision instead.

When to Use Which

Element Best for
Split by Field Value Simple branching on one field's possible values (e.g., a picklist or status field)
Split by Date Simple branching on a single date comparison (before/after/between/on a date)
Decision Any branch that needs multiple criteria combined within the same path
Split elements trade flexibility for clarity — reach for them first when a branch is genuinely single-condition, and fall back to Decision the moment a path needs more than one thing to be true.

Q&A

1.What release introduced Split by Field Value and Split by Date?

Winter '27.

2.What does the Split by Field Value element do?

It evaluates a chosen field or resource and creates a separate path for each configured value, with a built-in Default Path for values that don't match any configured path.

3.What operators does Split by Date support?

Before, Between, After, and Is On — each path can compare against its own date value or resource.

4.What is the single biggest limitation of both Split elements compared to Decision?

Neither lets you define multiple criteria within the same path — each path can only test one condition, unlike Decision, which supports compound, multi-criteria logic per path.

5.Can the Default Path in Split by Field Value be renamed?

No — the default outcome's name can't be changed, unlike the other configured paths.

6.When should you choose Decision over a Split element?

As soon as a branch's logic needs more than one condition to be true at the same time — Split elements only handle single-condition branching per path.

7.What's a good real-world use case for Split by Date?

Branching flow logic based on SLA deadlines, contract renewal windows, or record aging — any scenario where the only thing driving the branch is how a date relates to today or another date.

Closing thought: Split by Field Value and Split by Date won't replace Decision, but for the large share of flows that only ever branch on one condition, they make the canvas easier to read at a glance — which is a real win for long-term maintainability.
