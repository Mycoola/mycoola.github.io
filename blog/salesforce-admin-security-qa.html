Salesforce Admin, Security & Data Access Q&A

August 2026  ·  Original notes based on Salesforce Help and Admins documentation

Notes on core administration topics: permissions, record-level access, sharing and locking at scale, account/contact relationships, territory management, and everyday org objects like Activities and Campaigns.

Permissions and Access

1.What is the difference between a profile and a permission set?

Every user has exactly one profile, which sets a baseline of permissions and access. Permission sets add extra permissions on top of that baseline without changing the profile, letting admins grant narrow, specific access to a subset of users without cloning entire profiles.

2.Why does field-level security need to be checked in addition to record sharing?

Sharing determines whether a user can see a record at all. Field-level security determines which fields on that visible record they can read or edit — a user might see a record but not every field on it, so both layers have to align with the intended access model.

3.What is masking used for in a Salesforce org?

Data masking obscures sensitive field values (like SSNs or financial data) for users or environments that don't need to see the real values — commonly used in sandboxes so realistic test data doesn't expose production-sensitive information.

Record Access at Scale

4.What is data skew, and why does it cause performance problems?

Data skew happens when too many child records point to one parent (or too many records are owned by one user/group). Sharing recalculation and record locking become expensive when a single parent or owner has an outsized number of associated records.

5.What causes a "group membership operation already in progress" error, and why is it treated as a locking issue?

Group membership changes (adding/removing users from roles, groups, or territories) trigger sharing recalculation, which locks related records during processing. Concurrent membership changes on overlapping groups can collide, producing this lock-contention error.

6.What is the difference between original and enterprise territory management?

Enterprise Territory Management is the newer, more flexible model supporting multiple territory hierarchies and more granular assignment rules, while original Territory Management is the legacy, simpler model — new implementations default to the enterprise version.

Everyday Objects and Setup

7.What is an account team, and when is it useful beyond standard account ownership?

An account team lets multiple users collaborate on a single account with individually defined roles and access levels, useful when more than one person (sales rep, support contact, executive sponsor) needs tailored visibility into the same account.

8.Why does "who has access to campaigns" need its own documentation rather than following standard sharing rules?

Campaign access has its own visibility model separate from the standard sharing model, tied to marketing user permissions — a common point of confusion since it doesn't behave like sharing rules on typical custom or standard objects.

9.What determines when automation rules execute relative to each other?

Salesforce defines a specific save order for validation rules, workflow rules, flows, and triggers. Understanding this order is necessary to predict which automation sees which version of a record's data during a single save operation.

10.Why would an org need multiple Salesforce user license types?

Different license types (Full user, Platform, Chatter Free, etc.) grant different feature access at different cost points — matching license type to actual job function keeps licensing costs aligned with what each user role actually needs.

Sources: Salesforce Help documentation and Designing Record Access for Enterprise Scale (Salesforce Developers). These are original notes and summaries, not reproduced source material.
