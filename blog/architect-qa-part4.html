Salesforce Architect Interview Q&A — Part 4: Integration Architecture

Updated August 2026  ·  Part 4 of 4  ·  25 questions
Salesforce Architect Interview Series (100 questions) Part 1: Application Architecture Part 2: Data Architecture & LDV Part 3: Sharing & Visibility Part 4: Integration Architecture

The final part of the Architect series, aligned to the Integration Architect certification domain, covers enterprise integration patterns, API strategy, and event-driven design at scale.

Integration Patterns

1.What are the four core enterprise integration patterns relevant to Salesforce?

Request-Reply (synchronous call-and-wait), Fire-and-Forget (async, no confirmation needed), Batch Data Synchronization (scheduled bulk sync), and Remote Call-In (an external system calling into Salesforce's exposed APIs) — most real integrations combine several of these patterns.

2.What factors determine the choice between synchronous and asynchronous integration at an architectural level?

Business tolerance for latency, whether the calling process needs an immediate confirmation to proceed, the reliability/availability of the target system, and the volume/frequency of calls — high-volume, latency-tolerant scenarios favor async; low-volume, decision-blocking scenarios favor sync.

3.What is the Circuit Breaker pattern and how does it apply to Salesforce integrations?

A pattern that stops sending requests to a failing downstream system after a threshold of consecutive failures, "opening the circuit" to avoid overwhelming an already-struggling system and wasting resources on calls likely to fail — implemented via middleware or custom Apex logic tracking recent failure rates before attempting a callout.

4.What is the Saga pattern and when is it relevant to Salesforce integration design?

A pattern for managing a multi-step, multi-system transaction where a traditional distributed transaction/rollback isn't possible — each step has a corresponding compensating action to "undo" it if a later step fails, relevant when a Salesforce process spans multiple external systems that must stay logically consistent without true two-phase commit support.

5.How do you design integration architecture for a scenario requiring guaranteed message delivery?

Use a durable message queue or middleware with guaranteed at-least-once delivery semantics (rather than a simple HTTP fire-and-forget), combined with idempotent processing on the receiving end so a duplicate delivery (which at-least-once guarantees can produce) doesn't cause incorrect duplicate data.

API Strategy

6.What Salesforce APIs are available and when would you use each?

REST API — general-purpose, JSON, good for most integrations. SOAP API — XML-based, used for legacy system compatibility. Bulk API 2.0 — large data volume load/extract. Streaming/Pub-Sub API — real-time event consumption. GraphQL API — flexible, client-specified queries reducing over-fetching for modern app integration.

7.What is API-led connectivity and why does it matter for a large enterprise?

Structuring integrations into System, Process, and Experience API layers to maximize reuse and reduce point-to-point coupling. It matters at enterprise scale because without this layering, every new integration tends to be built from scratch, multiplying maintenance cost as the number of integrated systems grows.

8.How do you design an API versioning strategy to avoid breaking existing integration consumers?

Use explicit versioning (URL path or header-based) so breaking changes ship as a new version while existing consumers continue using the prior version until they migrate, combined with a documented deprecation timeline communicated well in advance of retiring an old version.

9.What is rate limiting and how do you architect around Salesforce's API call limits?

Salesforce enforces a rolling 24-hour API call limit per org edition/license count. Architect around it by favoring Bulk API for high-volume operations (which consumes limits differently and more efficiently than many small REST calls), caching results where freshness tolerance allows, and monitoring consumption proactively rather than discovering the limit was hit in production.

10.What is the difference between the Composite API and making multiple separate REST calls?

The Composite API bundles multiple sub-requests into a single API call/round-trip, reducing network overhead and API call consumption, and supports referencing the output of one sub-request as input to another within the same call — useful for integrations that need to create related records in one atomic-feeling operation.

Event-Driven Architecture

11.What is the Pub/Sub API and how does it differ from the legacy Streaming API?

Pub/Sub API is the modern, gRPC-based event streaming interface supporting higher throughput and better client language support than the legacy CometD-based Streaming API — new event-driven integrations should default to Pub/Sub API rather than the legacy option.

12.How do you design for event ordering guarantees in an event-driven Salesforce architecture?

Understand that Platform Events and CDC generally don't guarantee strict cross-object ordering by default in all delivery scenarios; if strict ordering matters for correctness, design consumers to handle out-of-order delivery gracefully (e.g., using a sequence/timestamp field to reconcile) rather than assuming delivery order matches publish order.

13.What is the difference between a Platform Event and a Standard/Custom Notification?

A Platform Event is a structured data message for system-to-system or process-to-process communication, consumed programmatically. A Notification is a user-facing alert meant to be seen by a human in the UI or via mobile push — they serve fundamentally different audiences even though both use an event-like publish mechanism internally.

14.How would you architect a real-time dashboard that reflects changes across multiple Salesforce orgs?

Use Change Data Capture or Platform Events published from each org, consumed by a central aggregation service (custom app or middleware) that maintains the unified real-time view, rather than having the dashboard poll each org individually, which doesn't scale well and adds latency.

15.What is event replay and why is it useful in Pub/Sub API-based architectures?

The ability to re-consume events from a specific point in the event stream's retention window (rather than only new events going forward) — useful for recovering from a consumer outage without losing events that were published while the consumer was down.

Legacy System Integration

16.How do you architect an integration with a legacy system that only exposes a flat-file export/import mechanism?

Design a scheduled batch process (via middleware or a Scheduled Flow/Batch Apex combined with an SFTP-capable integration tool) that picks up the file on a defined cadence, validates and transforms it, and loads it via Bulk API — accepting the inherent latency of file-based exchange rather than forcing a real-time pattern the legacy system can't support.

17.What is an Anti-Corruption Layer and why would you introduce one when integrating with a legacy system?

A translation layer that isolates your clean Salesforce data model from a legacy system's outdated or inconsistent data structures/semantics, preventing legacy technical debt from leaking into and corrupting the new system's design.

18.How do you handle data type/format mismatches between Salesforce and an external system during integration design?

Define explicit field-level transformation rules in the middleware or integration layer (date format conversions, picklist value mapping, currency/unit conversions) documented in a data mapping specification, rather than relying on implicit, undocumented assumptions that break silently when either system's data changes shape.

Integration Governance & Monitoring

19.What should an integration logging strategy capture for effective troubleshooting?

Request/response payloads (or at least a summary/hash if payloads are sensitive), timestamps, correlation Ids to trace a single business transaction across multiple systems, and success/failure status with error details — without this, diagnosing an intermittent integration failure becomes guesswork.

20.What is a correlation Id and why is it critical in a multi-system integration architecture?

A unique identifier attached to a business transaction as it flows across multiple systems, allowing logs from each system to be joined together to reconstruct the full journey of a single request — without it, tracing a failure across three or four hops becomes nearly impossible.

21.How do you design monitoring/alerting for a critical integration to catch failures proactively rather than reactively?

Set up automated alerts on failure rate thresholds, queue backlog depth, and unusual latency (not just complete outages), routed to the team responsible, so integration health degradation is caught before it becomes a business-visible incident reported by an end user.

22.What governance process should exist before a new integration is added to a mature Salesforce org?

A review of the integration's expected volume/frequency against API limits, its authentication approach against security standards, its error-handling design, and its impact on existing automation on the objects it touches — ideally as a lightweight architecture review gate rather than an ad hoc, unreviewed addition.

23.How do you decide which system should own conflict resolution when two systems can both update the same data?

Designate a clear system of record per data domain up front so conflicts are resolved by rule (that system always wins) rather than requiring case-by-case manual resolution, and design the integration to enforce that rule automatically rather than relying on process/discipline alone.

24.How would you architect a "kill switch" for a problematic integration in production?

Build a Custom Metadata Type or Custom Setting toggle that automation/Apex checks before executing an integration call, so a misbehaving integration (e.g., flooding an external system with erroneous calls) can be disabled instantly by an admin without a code deployment.

25.What's your overall framework for evaluating whether a proposed integration architecture is production-ready?

Confirm it handles failure gracefully (retries, idempotency, alerting), respects both systems' rate/volume limits at projected scale, has clear ownership and monitoring, uses a secure, least-privilege authentication method, and has been tested against realistic failure scenarios — not just the happy path — before it's approved for production traffic.
