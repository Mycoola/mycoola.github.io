Salesforce Consultant Interview Q&A — Part 2: Data Model & Sharing Design

Updated August 2026  ·  Part 2 of 4  ·  25 questions
Salesforce Consultant Interview Series (100 questions) Part 1: Discovery & Requirements Part 2: Data Model & Sharing Part 3: Automation & Integration Part 4: Migration & Governance

This part covers the object modeling and sharing/security design decisions a consultant must make before any configuration begins.

Data Model Design

1.When should you extend a standard object versus create a custom object?

Extend a standard object (Account, Contact, Opportunity) when the concept genuinely matches its built-in semantics and you want to inherit related features (forecasting, standard reports, AppExchange compatibility). Create a custom object when the concept is fundamentally different or when standard object limits/behavior would force awkward workarounds.

2.How do you decide between a Lookup and a Master-Detail relationship during data model design?

Use Master-Detail when the child record has no meaning without its parent (e.g., Order Line Items without an Order) and you need cascading delete or roll-up summaries. Use Lookup when the child can exist independently or when the relationship might need to become optional or change later — Master-Detail is much harder to convert after data exists.

3.What is a junction object and when do you need one?

A custom object with two Master-Detail relationships used to model a many-to-many relationship between two objects (e.g., linking Contacts to multiple Accounts they're affiliated with, beyond the single primary Account). It's the standard pattern since Salesforce objects only support one direct parent per Master-Detail relationship.

4.What are the trade-offs of using record types versus separate custom objects for variations of the same concept?

Record types keep data in one object with shared reporting and fewer relationships to manage, good when the variations share most fields and processes. Separate objects make sense when the variations have fundamentally different fields, security needs, or automation, since cramming unrelated concepts into one object with many record types becomes hard to maintain.

5.How do you design a data model to support multiple business units on one org?

Use a combination of record types for process variation, a business unit lookup field for segmentation/reporting, and sharing rules or Enterprise Territory Management to control visibility — while keeping shared master data (like Accounts) genuinely shared rather than duplicated per unit.

6.What is denormalization and when is it appropriate in a Salesforce data model?

Denormalization means storing redundant/derived data (e.g., a roll-up or a copied field) rather than always computing it live. It's appropriate when you need that value in contexts a formula can't reach (e.g., across a non-Master-Detail relationship) or need it snapshotted at a point in time rather than always current.

7.How many custom fields is "too many" on an object, and how do you prevent field sprawl?

There's no fixed number, but field sprawl becomes a problem when users can't find the fields they need or when page layouts become unusable. Prevent it by challenging every new field request against existing fields, using field-level help text and clear naming conventions, and periodically auditing field usage with tools like Salesforce Optimizer.

8.What's your approach to naming conventions for custom objects and fields?

Consistent, descriptive, and human-readable labels (not clever abbreviations), a documented convention for API names (e.g., prefixing by domain area), and avoiding generic names like "Status_2" that give no context to the next developer or admin who inherits the org.

9.How do you handle a data model requirement that conflicts with Salesforce's Master-Detail cascading-delete behavior?

If the child records must survive independently of the parent (auditability, historical reference), use a Lookup relationship instead and replicate needed automation (like roll-ups) via Flow or Apex triggers, accepting the added maintenance for the flexibility gained.

10.What is an External Id field and why is it important for integrations?

A custom field marked as External ID lets you uniquely identify a record using a key from an external system, enabling upsert operations (insert-or-update in one call) that are essential for idempotent integration and data migration design.

Sharing & Security Architecture

11.What factors determine your Org-Wide Default (OWD) setting for an object?

Start from the most restrictive setting that matches the business's actual default visibility need — Private if most records should only be visible to their owner and explicitly shared team members, Public Read/Write only if broad visibility is genuinely required by default. It's easier to open access via sharing rules than to retroactively restrict it.

12.How do you decide between a sharing rule and manual sharing?

Sharing rules apply automatically based on criteria (record owner's role/group, or field values) and scale to any number of records — use them for any recurring, predictable access pattern. Manual sharing is a one-off, user-initiated grant for exceptional cases and doesn't scale as a primary access strategy.

13.What is the role hierarchy and how does it affect record visibility?

The role hierarchy grants users above a record owner in the hierarchy the same level of access the owner has (if "Grant Access Using Hierarchies" is enabled, which it is by default for most objects), used to model management visibility (a manager sees their team's records) without individual sharing rules per user.

14.What's the difference between a Public Group and a Role for sharing purposes?

A Role represents a position in the organizational hierarchy and grants hierarchical visibility automatically. A Public Group is a flexible, admin-defined collection of users, roles, or other groups used purely for sharing/visibility purposes without implying any reporting structure.

15.When would you use Territory Management instead of the standard role hierarchy?

When account/opportunity assignment needs to be based on criteria like geography, industry, or account size rather than strictly who owns the record — common in sales orgs where multiple reps need shared visibility into the same accounts based on territory rules rather than direct ownership.

16.What is a permission set and how does it differ from a profile?

A profile defines a user's baseline permissions and is assigned exactly one per user (mandatory). A permission set grants additional permissions on top of the profile and can be assigned to multiple users regardless of their profile — the recommended approach is minimal profiles plus composable permission sets, rather than dozens of near-duplicate profiles.

17.What is a permission set group?

A bundle of multiple permission sets assigned as a single unit, simplifying user provisioning when a role consistently needs the same combination of permission sets (e.g., "Sales Rep" = three specific permission sets bundled together and assigned in one action).

18.How do you design security for an object that needs to be visible externally (e.g., via Experience Cloud/Community)?

Use Sharing Sets or Share Groups (for high-volume/authenticated external users) tied to the external user's account/contact, combined with a restrictive OWD, and always verify guest user access is scoped as tightly as possible since misconfigured guest access is a common Salesforce security finding.

19.What's the risk of over-relying on "without sharing" Apex classes in a design?

It can quietly bypass the org's intended sharing model, exposing data across business units or to users who shouldn't see it, and can be difficult to audit later since the access isn't visible in the standard sharing configuration UI. It should be a deliberate, documented exception, not a default habit.

20.How do you approach field-level security design across many profiles?

Default to permission sets for field visibility (rather than editing dozens of profiles individually) so access is composable and auditable, and periodically review field-level security alongside object permissions using tools like the Permission Set/Profile comparison reports.

Multi-Business-Unit & Complex Org Design

21.What is Enterprise Territory Management and when would you recommend it over basic Territory Management?

Enterprise Territory Management is the modern, more flexible territory model supporting multiple territory models, more granular rule-based assignment, and better reporting — it's the right recommendation for any new implementation needing territory-based sharing, since the original Territory Management feature is legacy.

22.How do you decide between one org and multiple orgs for a multi-business-unit company?

Favor one org whenever business units share enough common data/processes to benefit from unified reporting and a single source of truth — multiple orgs add real integration and reporting overhead. Consider separate orgs only when regulatory/data-residency requirements or fundamentally incompatible processes make a single org genuinely unworkable.

23.What is a Business Unit field pattern and how does it support multi-BU reporting?

A required picklist or lookup field present on key objects identifying which business unit a record belongs to, used consistently in report filters, sharing rules, and automation criteria so BU-level reporting and access control stay consistent across the org without needing separate objects per unit.

24.How do you handle a requirement for one business unit to see only their own data while another needs cross-BU visibility?

Set OWD restrictive enough for the unit needing isolation, then use a sharing rule or public group specifically for the cross-BU role/team that needs the broader view — this keeps the default safe while granting the necessary exception explicitly and auditable.

25.What questions do you ask to determine the right sharing model before implementation starts?

Who owns each type of record day-to-day? Who needs visibility beyond the owner, and why (manager oversight, cross-functional collaboration, external partner access)? Are there any regulatory or contractual data segregation requirements? Answering these before configuring OWD prevents a costly sharing model rebuild mid-project.
